# game-arcade 次作企画：共通実行ルール

このファイルは、`ToramaruA/game-arcade` の次作企画を自動で決める際の共通仕様です。GitHub の `[GAME]` PR Merge、Clef結果のPRコメント通知によるイベント起動、および朝6時・9時の補助確認を行う ChatGPT タスクから参照します。企画・評価・Issue 作成のルールはこのファイルを正本とし、二重管理しません。

## 起動条件と重複防止（最初と最後に必ず確認）

1. GitHub のPR Mergeイベントで起動した場合、**MergeされたPRのタイトルが `[GAME]` で始まらなければ何もせず終了**する。時刻指定の定期実行にはこの条件を適用しない。
2. 企画前に GitHub の最新情報を確認し、**タイトルが `[GAME]` で始まる open Issue または open PR があれば作成せず終了**する。PRをIssue検索で拾えても、見落とし防止のため両方確認する。
3. **企画・評価・詳細設計・レビューがすべて終わった後、Issue作成の直前にも再検索**する。open `[GAME]` Issue・PRが1件でもあれば作成しない。また今回の実行が始まった後に別タスクが作成した `[GAME]` Issueがあれば、既にclosedでも作成しない。
4. GitHubへのアクセスや検索に失敗したら、存在しないと決めつけてIssueを作らず、確認できなかったことを報告する。
5. Issueの作成は**1回の実行につき最大1件**。成功したらURLを報告し、何も作らなければ理由を報告する。
6. 確認とIssue作成の間には、不要な待機や別の作業を挟まない。この二重確認でも、完全に同時実行される場合の重複を数学的に排除できるわけではない。


## Clef審査の再開・重複防止
- 進行中の [GAME] Issue・PR がないことを確認したら、新案を考える前に **open の [CLEF-REVIEW] Issue** を検索する。既存の審査依頼があれば**それを再利用し、新しい審査依頼は作らない**。そのIssueの本文（候補案）と最新のActions作成コメントを読み、下記のClefステップから再開する。
- openの審査Issueがあるのに結果コメントがまだなければ、処理中として終了し、次のClef結果のイベント通知で再開する（取りこぼし時は補助確認で回復する）（自動化の1回の実行の中で長時間待つ必要はない）。
- 既存審査Issueが複数ある場合は新規作成せず報告する。作成直前にも [GAME] と [CLEF-REVIEW] を再チェックする。
- **審査は2段階**。Issue本文が従来形式（phase未指定）なら「企画選定」、JSONの `phase: "design"` なら「詳細設計の最終審査」。**同じ [CLEF-REVIEW] Issueを編集して再利用する**。2つ目の審査Issueを新規作成しない。
- 企画選定は `<!-- clef-game-idea-review:v1 -->`、詳細設計は `<!-- clef-game-design-review:v1 -->` の付いたActionsコメントを使う。結果はJSONで、企画段階は status / selected / ranking / choice_probabilities、詳細設計は status / revision / scores / ready_to_build_probability / weak_areas を含む。
- **再開時にIssue本文のphaseを最優先で確認する**。phase=designなら元の複数企画の審査をやり直さず、4.8の結果確認・再設計・Issue作成へ直行する。phase未指定なら3.5の結果確認から再開する。作成直後/編集直後でコメント未着なら今回は待機終了し、次回起動時に再開する。
- 詳細設計の結果を受け取る際は、Issue本文の `revision` と最新の詳細設計コメント内の `revision` が**同一**であることを確認する。一致しない結果や、本文編集以前に書かれた古いコメントを採用しない。改訂時はrevisionを1増やす。
- 企画選定の結果（候補ごとの採点）と、採用案・不採用理由を詳細設計Issue本文の `selection_record` に保存する。前段階のデータが失われないようにする。
- APIエラーや結果欠落では推測採点で代替しない。Issueを残して理由を報告する。結果を得られた場合も、[GAME] Issue作成直前に元の [GAME] 重複チェックを必ず実行する。


## 修正・ボツ・Cloudflare実上限への対応（2026-11-13）

- **同じ採用案の詳細設計は初稿＋修正2回、最大3回の審査まで**。回数は起動をまたいで保持し、同じ案を別ID・別Issueへ移してリセットしない。既存のrevision=1は初稿として数える。
- 不合格時はChatGPTが「修正する／早期ボツ／3回目不合格によるボツ」を根拠付きで判断する。**修正により実際のプレイ体験を改善できる見込みがある場合は修正を優先**し、同一案の初稿＋修正2回（審査最大3回）で合格できなければ必ずボツ。Clefの合格基準を下げたり、スコアを人為的に書き換えたりしない。
- **早期ボツの根拠を明文化する**：①プレイヤーが繰り返す具体的操作と判断のトレードオフが成立しない、②数回で正解が固定化し追加ステージでも遊びが変化しない、③指定技術・制作範囲で核となるルールを実現できない、④過去の不採用作品と失敗の核が実質同じ、のいずれかが設計の中核にあるか確認する。ただし欠点があるだけで自動的にボツにしない。残りの修正枠で**ルール・行動・結果・難易度・中身**を具体的に変更して救えるなら修正する。設計の主軸を別ジャンルへ全面交換しなければ救えない場合、または核の成立を具体例で説明できない場合だけ早期ボツを選ぶ。「低スコアだから」「ChatGPTが面白くないと思った」だけのボツは禁止。
- **判断記録（必須）**：前回の実際の1分間のプレイ例、失敗する場面（操作・選択・状態変化）、根本原因、修正で変えるゲーム内ルールと新しいプレイ例、残り修正回数を比較する。「早期ボツ」なら改善策を最低1案検討したうえで、なぜ修正2回以内に根本問題を直せないか具体的に書き、後続候補へ進む。曖昧なら早期ボツを決め打ちせず1回修正して検証する。
- **点数目当ての文章修正を防ぐ**：修正のたびに「問題／変更する具体的なルール・操作・敵やステージの挙動／変更前と変更後の1分間のプレイ例／改善する理由」をselection_recordへ記録する。文体、形容詞、評価用の言い回し、宣伝文だけを変える再提出は禁止。修正後の設計JSONの該当フィールドにも、実装可能な変更を反映する。設計内容に実質的な差分がない場合は同じrevisionの再審査を行わず、ルール変更案を考え直すかボツにする。Clefは修正理由・修正案を出さないため、採点とChatGPTの分析を明確に区別する。
- ボツの理由、各案の審査回数・revision・結果、修正履歴をselection_recordに保持する。残った候補を過去の評価・不採用理由から再検討し、適切な候補がなければ新規発案する。企画選定のClef審査から再開し、同じ審査Issueを使う。phaseを戻す前に全記録をIssueコメントにも保存する（企画用JSONはselection_recordを引き継がないため）。次の詳細設計へ戻す際に記録を復元する。revisionはIssue内で単調増加させ、案ごとの初稿・修正回数とは区別する。
- **Clef APIの自主的な1日5回制限は廃止**。企画選定・詳細設計・ボツ後の別案などの審査回数に共通の日次上限は設けない。詳細設計の「初稿＋修正2回」の不合格上限は別ルールとして維持する。
- GitHub Actionsは`@cf/cloudflare/clef`を実際に呼び、Cloudflare Workers AIがHTTP 429かつ内部コード`3036`（1日10,000 Neuronsの無料枠を消費）を返した場合だけ`status=deferred`・`retry_after=翌UTC 00:00`を審査Issueに記録してPR #70へ中継する。**HTTP 429だけでは日次上限とみなさない**（`3040`は一時的な容量不足）。不明なAPI失敗は`error`とし、推測採点や無限再試行をしない。
- **Cloudflareの実上限に達したときだけ保留**する。`deferred`・APIエラー・結果未着を不合格に数えず、設計をボツにせず、詳細設計の修正2回にも数えない。`retry_after`（通常日本時間09:00）より前に再実行しない。再試行時は同じ案・同じphase/revision・同じJSONのまま、Issue本文の末尾改行など最小限の編集でGitHub Actionsを再起動する。無料枠はCloudflareアカウント内のほかのWorkers AI利用とも共有する。課金プランへの変更や有料枠での自動超過利用は行わない。
- **利用上限中でも**、すでに届いている有効な合格結果から[GAME] Issueを作る処理は進めてよい（新しいClef呼び出しはないため）。
- **審査再開（イベント駆動）**：GitHub ActionsはClef結果を元Issueに投稿した直後、PR #70（イベント受信専用としてopenのまま維持）にも `<!-- clef-review-relay:v1 -->` と元Issue番号・元コメントID・phase・revision・statusを含むbotコメントを投稿する。このPRコメントをChatGPTのイベントタスクが受信し、元の判定コメントを再取得・検証して処理する。転送するのは通知用メタデータだけであり、判定の正本は元Issueのコメントと本文。遅延・重複に備えて元コメントID、phase、revision、最新結果を照合する。別PR・別bot・人間コメント・自己返信・古い結果には反応しない。イベントの即時配信・実行開始はプラットフォーム依存で厳密な秒数は保証しない。新規企画を始めるのは朝6時または[GAME] PR Mergeからのみ。PR Mergeタスクの起動条件は変更しない。
- 定期タスクは日本時間06:00（従来どおり新規企画開始・通常の取りこぼし回復）と09:00（**Cloudflare Workers AIの実上限コード3036で保留された審査の再開専用**）に限定し、毎時ポーリングはしない。09:00回は、現行open [CLEF-REVIEW] Issueの最新有効判定が`status=deferred`で、`reason`にCloudflareの日次無料枠超過コード`3036`が明示され、`retry_after`到来済みであり、同じphase/revisionの再提出が未実施であることを検証できた場合に限り、同じ設計・revisionの再審査を1回だけ起動する。その他のstatus（ok/revise/error/結果未着）や審査Issueなし、イベント取りこぼしは09:00回で変更しない。結果はbotコメントイベントで処理する。時刻指定起動時はmainの本改訂と`scripts/clef-cloudflare-error.mjs`の存在を確認し、未反映なら読み取りのみ・無通知終了する。
- 実上限による`deferred`は`retry_after`（UTC 00:00＝日本時間09:00）より前にAPIを再試行しない。09:00補助タスクでは、最新結果が`3036`による`deferred`で、同じphase/revisionの再提出済みでないことを厳格に確認してから、同じ本文・revisionで最小編集を1回行う。一般的なHTTP 429（`3040`など）やAPIエラーは09:00専用処理の対象外。結果未着だけを理由に本文を編集しない。GitHub Actionsの該当ジョブが実行中・待機中なら終了し、失敗／キャンセルを含めジョブ状態を確認できない限り09:00回で再提出しない。重複起動を避けるため再提出直前にIssue本文・最新コメント・ジョブを再確認する。

- イベント処理時はリレーのsource_issueがopenの [CLEF-REVIEW] Issueか確認し、元コメントの投稿者github-actions[bot]、所定の審査マーカー、phase、revision、statusを照合する。転送されたJSONだけで合否を決めず、元Issue本文と最新結果を確認する。同じ元コメントIDを二重処理しない。イベント取りこぼしは朝06:00の補助タスクで回復する。09:00回は実上限コード3036のdeferred専用とする。

## 企画・評価・詳細設計・Issue作成

あなたは ToramaruA/game-arcade の企画チームです。全員が**ヒット作を何本も出してきた一流のゲームプロデューサー／ゲームデザイナー**として考えてください。次に作るブラウザゲームを1本決め、GitHub Issue を1件作ってください。

**前提（オーナーの実感）**：見た目と一発ネタだけでは面白くならない。**ある程度中身が凝っていないと面白くならない**。「アイデアの面白さ」ではなく「遊んで面白いか（遊びの核・判断の深さ・中身の量・手触り）」で考える。過去に不採用になった作品（`docs/taste.md` の「微妙だったもの」「遊んだ感想の記録」）の失敗理由を必ず踏まえる。

**土台は「実績のある遊び」、個性は「世界観・ストーリー・中身の量」で出す**（2026-11-09 追加）：
- 不採用になった作品の多くは、**見たことのない一発ギミック**（ダイヤルを選ぶ、撃って眺める、分岐を選ぶ等）を土台にしていて、遊ぶと浅く、意味も分かりづらかった。好評だった「風の庭」は、倉庫番のような**実績ある箱庭パズル**を土台に、絵本の世界とステージ数・収集・着せ替えで厚みを出したもの。
- 各案は「**土台にするジャンル**（例：箱庭パズル、ローグライト、デッキ構築、タワーディフェンス、アクションRPG、ベルトスクロール、探索アドベンチャー、経営・育成、リズム、落ち物パズル、ノベル＋パズル）」と、そこに**何を足して個性にするか**をはっきり書く。特定の既存作品の再現はしない。
- **ストーリーのある凝った作品を積極的に**：3人のうち1人以上は、物語で引っ張る案を出す（登場人物、章立て、遊びと絡む出来事、選択や成績で変わる結末）。物語は長文で読ませず、遊びの中で少しずつ見せる。
- **中身の量の目安**：全体で30分〜数時間遊べる（例：風の庭の3ワールド×5ステージ・45個の収集・着せ替え）。1回5分で終わる小品にしない。
- **分かりやすさ**：ルールを一文で言えること。初見の人が説明を読まずに30秒で「何をすればいいか」分かること（最初のステージを手引きにする）。

1. 好みと過去作品の確認：
   - docs/taste.md（オーナーの好みメモ）を必ず読む。いちばん重視する基準はここに書いてある。
   - site/games/games.json と過去の [GAME] Issue（closed 含む）を読み、作った作品・過去の候補・不採用理由を把握する。
2. 発案：3人の企画担当として、それぞれ異なる方向性から1〜2案ずつ出す。
   - 方向性：好みメモの「気に入っていた企画」や「当たり方」を発展させる／強い世界観を持つ新規案／**直近の作品と違うジャンル・画風に挑戦する案**（3人のうち1人は必ずこれ）。
   - **いろいろなパターンを試す**：ジャンル（パズル・アクション・言葉遊び・散歩や探索の雰囲気ゲー・リズム・育成・シミュレーションなど）と画風（ドット絵レトロ・かわいい3D・パステルの絵本調・水彩・切り絵・ネオン・ミニマルなど）を毎回変える。**直近2作と同じジャンル・画風の組み合わせは採用しない**。レトロ一辺倒にしない。
   - 各案に「最初の画面の絵」を文章で具体的に描写する（背景・主役・画面に並ぶ情報・色・画風・動き）。
   - **各案に「なぜ面白いのか」の説明を付ける**（2026-11-10 追加）。ゲームを知らない人に向けて、次の3つを書く。説明できない案は出さない。
     - **遊んでいる様子の実況**：「〇〇が来たので△△して、□□になって、思わず『あっ』となる」のように、実際の1分間を具体的に。
     - **たまらない瞬間**：いちばん気持ちいい・悔しい・笑える瞬間を1〜3つ。
     - **もう1回やりたくなる理由**：次はどうしたいと思うか。
   - 日常の小ネタや、図形とボタンだけで成り立つ地味な案は出さない。過去作品と重複させない。
   - 3D（Canvas の WebGL を自前で書く、または CSS 3D）や、Web Audio で鳴らすBGM・効果音も使ってよい（外部素材・CDN なし）。
3. 評価：2人の評価担当が独立に、次の基準を5段階で採点し理由を書く。
   - 見た目のつかみ（スクリーンショット1枚で、知らない人がやってみたくなるか）※最重視・2倍で数える
   - 見せたくなる体験（結果や展開を人に話したく・共有したくなるか）
   - 面白さ（最初の数秒・遊びの核の深さ・中身の量・再プレイ性）。**「ルールを読んだだけで、10分遊んでも飽きないと言えるか」**で採点する。土台のジャンルが実績ある遊びか、ルールを一文で言えるかも見る。一発ギミックだけの案は3点以下
   - 独自性（直近の作品と違うジャンル・画風への挑戦も加点）
   - 実現性は点数にせず、合否だけ判定する（外部素材なしの HTML/CSS/JS と Canvas・SVG の描画で、1回の PR で遊べる形まで作れるか）。「作りやすいから」を採用理由にしない。
3.5 **Clefによる独立した企画審査（必須）**：
   - 2で作った案の中から発案済みの2〜6件を評価対象にする。**ChatGPTの採点・自己批評と別に**、Cloudflareの判断特化型AI ClefがGitHub Actionsから採点する。
   - タイトル「[CLEF-REVIEW] 企画審査 <日付・短い識別名>」で通常のGitHub Issueを1件作成。タイトルは[GAME]にしない。本文は**JSONのみ**（またはjsonコードブロック）。次の形式を用いる：
     - ルート：schema_version: 1、context:（好み・過去失敗例・企画目標を簡潔に書いた文字列、2000文字以内）、candidates:（2〜6件の配列）。
     - candidatesの各要素は **id: A, B, C... の連番**、title、genre、core_loop、one_minute、highlight、replay、visual、feasibilityを**すべて具体的な文字列**で含める。各フィールド850文字以内、本文全体18000文字以内。
     - 例：{"schema_version":1,"context":"重要なのは遊びの核と繰り返し遊べること","candidates":[{"id":"A","title":"企画A","genre":"探索パズル","core_loop":"毎ターン経路と道具を選ぶ","one_minute":"敵に見つかりそうなので鍵を諦め迂回","highlight":"ギリギリの脱出","replay":"複数のマップと収集物","visual":"俯瞰の彩色マップ","feasibility":"JS+Canvasで実装"},{"id":"B",...}]}
   - Issue作成がGitHub Actionsの **Clef game planning review** を起動する。**APIトークンはGitHub Secretsにあり、ChatGPTタスクから直接参照できない**。GitHub ActionsがそのIssueに判定コメントを書き込む。
   - Issueのコメントを確認する。結果コメント未着なら今回は「Clef審査待ち」で終了し、次の起動時に再開する。[GAME] Issueを作らない。
   - Clefは候補をchoiceで比較し、gameplay・replay・visual・shareを各0〜4点で評価する。評価の重みは45%・25%・15%・15%。**結果のselectedを第一候補として採用する**。ただし、根拠を伴う明らかな実現不能・既存ゲームとの重複などがあれば、その理由をIssueへ記載し案を再設計する。数値を実証済みの楽しさだとはみなさない。
   - status=reviseなら候補の核を再設計して同じ審査Issueの本文を編集し再審査する（最大1回/起動）。status=errorなら結果を捏造せず終了。status=okでselectedがある場合にのみ4へ進む。
   - 最終的な[GAME] Issueの「選定の記録」には**Clef審査IssueのURL・採用ID・全候補の点数とAIによる判断の限界**を含める。[GAME] Issueを作成できたら、[CLEF-REVIEW] Issueをcloseする（詳細設計審査にも再利用するため**その前には閉じない**）。
   - 並行起動による二重作成は完全に排除できないため、審査依頼作成の直前もopen [CLEF-REVIEW] と [GAME] の両方を確認する。
4. 選定：最終選定担当がChatGPTの評価と**Clefの独立判定**を照合して1案を選び、採用理由と主な不採用理由を書く。**採用理由は「面白さの説明」に納得できたかで書く**（点数だけで選ばない）。
4.5 詳細設計：採用した案について、一流のゲームプロデューサーとして**遊べる設計書**まで詰める。抽象的な言葉（「驚き」「やり込み」）で終わらせず、具体例を書く。
   必ず考える：
   - **遊びの核を一文で**：プレイヤーが毎回「何を考えて、何を決めるか」。その判断に正解が1つに決まらない理由
   - **ループ**：数秒単位（1操作ごとの手応え）／数分単位（1ステージ・1回のプレイ）／何日か（また来たくなる理由）
   - **中身の量と具体例**：ステージ・敵・アイテム・イベント・言葉・組み合わせなどの数と、**実際の中身を最低10個は書き出す**（例の一覧そのものが設計）。そのうち「これあるの！」と驚く仕込みも書く
   - **難易度と成長の曲線**：最初の30秒で分かること、5分後に分かること、慣れた人が狙うこと。新しい要素をいつ出すか
   - **手触り**：操作した瞬間の反応（動き・音・演出）、成功と失敗の気持ちよさ
   - **飽きる地点とその対策**：何回目・何分目で飽きそうか、そこに何を足すか
   - 1プレイの流れ：何から始まり、どこで盛り上がり、どう終わるか
   - 画面設計：最初の画面と、いちばん盛り上がる場面の画面の構図
   ゲームに合う場合だけ考える（無理に付けない）：
   - 世界観・ストーリー：舞台、プレイヤーの立場、物語の起伏
   - 結末のバリエーション：選択や結果でどう変わるか。人に見せたくなる結果画面と共有文
4.6 辛口レビュー：別の担当が**厳しいプロデューサー**として設計を読み、「地味」「すぐ飽きる」「予想どおり」「見た目が弱い」に加えて、**「中身が薄い（判断がない・正解が1つ・数回で全部見える）」「選ぶだけ・眺めるだけになっている」**点を指摘し、主担当が直す（1回）。直しきれない根本的な弱さがあれば、案ごと差し替える。
4.7 **面白さの再説明**（作る前の最終確認）：詳細を詰めて直した後の設計で、もう一度「なぜ面白いのか」を説明し直す。
   - 2の3項目（実況・たまらない瞬間・もう1回やりたくなる理由）を、**設計した具体的なステージ・敵・仕掛けの名前を使って**書き直す。
   - 最初の説明から何が良くなったか、何が変わったかを一言で。
   - 再説明が最初より弱くなった・説明できない場合は、作らずに 4.5 に戻るか、案を差し替える。
4.8 **Clefによる詳細設計の最終審査（必須。制作前のゲート）**：
   - 4.5〜4.7を終えたら、既存の **[CLEF-REVIEW] Issueの本文をJSON形式で編集**し、`phase: "design"` に切り替える。これは `issues.edited` をトリガーに、同じGitHub ActionsがClefの別の採点基準で再審査する仕組み。**[GAME] Issueをまだ作らない**。
   - 必須のルートフィールド：`schema_version: 1`、`phase: "design"`、`revision: 1`（再設計のたびに増やす）、`context`（2500文字以内）、`selection_record`（以前の全候補・ChatGPT/ Clefの評価・選定理由を文章で残す。12000文字以内）、`idea_review_url`（その審査Issue自身のGitHub URL）、`selected_idea: {"id":"A", "title":"..."}`、`design`（以下の17項目の文字列）。
   - `design` に含めるフィールドは**すべて必須**：`title`、`genre`、`player_goal`（勝利条件・目的）、`core_decisions`（毎回の判断とトレードオフ）、`first_30_seconds`（操作・チュートリアル）、`minute_by_minute`（1プレイの流れ）、`short_and_long_loops`、`levels_and_content`（10個以上の実例・量）、`difficulty_progression`、`control_feedback`、`start_screen`、`climax_screen`、`failure_and_retry`、`replay_motivation`、`technical_scope`、`critical_review`（辛口レビューで指摘し直した点）、`fun_explanation`（4.7の具体的説明）。各フィールド3500文字以内、JSON全体42000文字以内。
   - **プレイの中身を実際の出来事として書く**。美辞麗句・抽象的な「面白い」「やり込み」ではなく、ステージ・敵・障害物・報酬・操作を具体名で書く。モデルが未記載の要素を勝手に補完しないようにする。
   - Clefは次の5項目をそれぞれ0〜4点で評価：**depth（判断の深さ）**、**longevity（10〜30分の飽きにくさ）**、**clarity（最初の30秒の理解しやすさ）**、**progression（上達・達成感）**、**coherence（ルール・画面・ステージの整合性）**。加えて `ready_to_build` をYes相当の確率（0〜1）で出力する。
   - 暫定の最低条件は depth≧2.5、longevity≧2.5、clarity≧2、progression≧2、coherence≧2.5、ready_to_build≧0.70。**5項目と確率のすべてを満たしたときだけstatus=ok**（コードで判定）。閾値は未検証の暫定値であり、実際に遊んだときの面白さを保証しない。
   - 結果の `weak_areas` にある低得点の項目は、**ChatGPTが具体的な問題を分析**して設計を修正する。Clefは点数と確率だけを出すので、修正案を説明したと偽らない。低得点なら同じIssue本文の `revision` を増やし、改善後の設計に更新する（1実行あたり最大1回）。更新直後は新しいコメント待ちで終了し、次のClef結果のイベント通知で再開する。同じ案は修正2回まで。初稿を含む3回目も不合格なら上記ルールに従ってボツとし、別案へ進む。
   - 最新の詳細設計結果が **status=ok** かつrevision一致である場合のみ5に進む。失敗・未着・revision不一致・エラーなら[GAME] Issueを作らない。
   - [GAME] Issueの「選定の記録」に、**企画段階と詳細設計段階の両方のClef結果**（5項目の点数と制作可否の確率）、審査IssueのURL、AI判定の限界を残す。詳細設計本文と `selection_record` を[GAME] Issueに引き継ぎ、元データを失わない。
Issue には 4.5 の内容を「詳細設計」として、4.7 の内容を「この遊びの面白さ」として、4.6 の指摘と直した点を「選定の記録」に書く。
5. Issue 作成：**4.8の最終審査合格後のみ** .github/ISSUE_TEMPLATE/game.md の形式で、タイトル「[GAME] <タイトル>」で1件だけ作る。
   - 「見た目・雰囲気」には、最初の画面の構図・配色・主役の絵・画面に並ぶ情報・画風・演出を、Claude Code が絵を描けるくらい具体的に書く。
   - 機能は、見た目と世界観を損なわない範囲で絞る。ただし**遊びの核と中身の量は削らない**（削るのはおまけの機能）。
   - 「この遊びの面白さ」（4.7）は Issue の上の方に置き、Claude Code が作るときの目標にする。
   - 「選定の記録」に 2〜4 の内容（各案の面白さの説明を含む）を残す。

複数の担当を分けて実行できない場合は、1人で順に役割を演じ、その旨を Issue の「選定の記録」に明記する。

## 保守

今後、企画・評価・Issue作成ルールを変えるときは、原則このファイルを修正する。2つの自動タスクには起動条件と本ファイルへの参照だけを書き、本文を重複させない。
